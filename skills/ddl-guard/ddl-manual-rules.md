# DDL 脚本无法检查的规则

以下规则 `ddl_check.py` 无法自动检查，审查时需逐表人工判断。

## 命名语义【强制】

| 规则 | 要点 | 操作指引 |
|---|---|---|
| 属性级别命名 | 字段名细化到属性级别，不得用主体名当属性名（如订单表字段不能叫 `order`） | 审查时检查每个字段名是否细化到具体属性。例如订单表中有 `order_no`（订单编号）、`buyer_id`（买家id），不应有 `order` 字段 |
| 内容视角命名 | 以存储内容含义命名，而非业务功能/逻辑视角 | 审查字段名是否反映存储内容的实际含义。例如存储"手机号"应叫 `mobile_no` 而非 `contact_method`（业务视角） |
| 泛化词 | 避免「关联」「业务」等无信息量词汇，有更精确的词则替换 | 审查表名和字段名是否包含「关联」「业务」等泛化词。例如 `order_business_rel` 应改为 `order_business_mapping`，`associate_id` 应改为具体业务含义的字段名 |
| 方/人区分 | 专指人用 `er`（中文名「xx人」），含机构用 `pty`（中文名「xx方」） | 审查涉及「人」和「方」的字段名。例如「联系人」用 `contact_er`，「合作方」用 `partner_pty` |
| 拼音 | 表名/字段名使用英文单词/缩写，禁止拼音或拼音缩写 | 审查所有表名和字段名是否为英文。发现拼音（如 `chanpin_mingcheng`、`danpai_jixiao`）立即要求改为英文 |
| 表名主体 | 表名围绕核心主体设计 | 审查表名是否围绕核心业务主体。例如 `order_process_log` 应改为 `order_log` 或 `order_event`，核心主体是 order 而非 process |

## 注释质量【强制】

| 规则 | 要点 | 操作指引 |
|---|---|---|
| 补充信息必要性 | 圆括号内容须为必要补充；冗余或让含义混淆的不写 | 审查注释中圆括号内容是否为必要补充。例如「订单状态[10-待支付,20-已支付,30-已完成]」是必要的，但「订单编号(订单号)」中括号内容冗余，应改为「订单编号」 |
| 字段与注释对应 | 字段名与注释含义对应、词汇对应 | 审查字段名和注释是否语义一致。例如字段 `contact_mobile` 注释应为「联系人手机号」而非「联系手机」，字段 `order_no` 注释应为「订单编号」而非「订单号」 |

## 设计合理性【推荐】

| 规则 | 要点 | 操作指引 |
|---|---|---|
| 复数形式 | 表名/字段名不使用名词复数（如不加 s） | 审查表名和字段名是否使用了名词复数形式。例如 `user_orders` 应改为 `user_order`，`biz_lines` 应改为 `biz_line` |
| 字符串长度 | 长度以实际内容为准、够用即可 | 审查 varchar/char 长度是否合理。例如 `varchar(500)` 存储简短字段应改为 `varchar(200)` 或更小 |
| 数据行长度 | 单行不超过 8020 字节 | 估算表所有字段长度总和，确保不超过 8020 字节（MySQL InnoDB 行格式限制） |
| NOT NULL + 默认值 | 字段尽量设 NOT NULL 并指定默认值 | 审查每个字段是否设置了 NOT NULL 和合理的默认值。例如 `varchar` 字段默认值应为 `''`，`tinyint` 字段默认值应为 `0` 或业务默认值 |

## 禁用语句【强制】

脚本只解析 `CREATE TABLE`，以下语句类型不会被检出：

| 规则 | 要点 | 操作指引 |
|---|---|---|
| 触发器 | 不得使用 `CREATE TRIGGER` | 审查 DDL 文件中是否包含 `CREATE TRIGGER` 语句，发现立即要求移除 |
| 存储过程 | 不得使用 `CREATE PROCEDURE` | 审查 DDL 文件中是否包含 `CREATE PROCEDURE` 语句，发现立即要求移除 |
| 视图/自定义函数 | 【推荐】不使用，确需时须经技术管理委员会评审 | 审查 DDL 文件中是否包含 `CREATE VIEW` 或 `CREATE FUNCTION` 语句。确需使用时，需提交技术管理委员会评审 |

## 需运行时验证【强制】

| 规则 | 要点 | 操作指引 |
|---|---|---|
| 索引有效性 | 索引字段须与查询条件一致，需 EXPLAIN 验证 | 1. 列出所有索引及其字段<br>2. 找出使用该索引的 SQL 查询<br>3. 对每个查询执行 `EXPLAIN` 或 `EXPLAIN ANALYZE`<br>4. 确认 `type` 列不为 `ALL`（全表扫描）<br>5. 确认 `key` 列确实使用了预期索引<br>6. 确认 `rows` 列与预期扫描行数一致 |

## 审查清单（逐表核对）

对每张表，按以下顺序逐条核对：

1. **表名**：是否围绕核心主体？是否使用英文？是否无拼音？是否无泛化词？是否无复数？
2. **表注释**：是否完整？是否 ≤ 64 字符？是否无特殊字符？
3. **字段名**：是否细化到属性级别？是否使用英文？是否无拼音？是否无泛化词？是否无复数？
4. **字段注释**：是否完整？是否 ≤ 128 字符？是否无全角字符？是否与字段名语义对应？
5. **字段类型**：是否使用禁用类型？（脚本已检查）
6. **必含字段**：是否包含 id/creator_id/create_time/last_updater_id/last_update_time？（脚本已检查）
7. **逻辑删除**：是否统一使用 `del_flag`？注释格式是否为 `删除标志[0-否,1-是]`？（脚本已检查）
8. **索引**：命名是否符合 `ix_`/`uk_` 规范？（脚本已检查）
9. **索引有效性**：是否通过 EXPLAIN 验证？（需人工运行）
10. **设计合理性**：字段数量 ≤ 40？单行 ≤ 8020 字节？NOT NULL + 默认值？字符串长度合理？
