# 审查报告输出规范

适用于本仓库所有审查类输出：`/ddl-guard`、`/api-guard`、`/arch-guard`、`/impact-guard`、`/contract-guard`
的「补充人工判断」部分，以及 CR 评审意见、设计评审回复。

> 机器可读部分（CI/脚本输出）由 [`docs/design/guard-receipt-spec.md`](../docs/design/guard-receipt-spec.md)
> 的收据信封承载；本规范约束**人读报告与 LLM 生成的审查结论**的输出结构。

## 核心原则
- 审查报告落盘到目标仓库的 docs/ 目录（或直接推送到 MR 评论），不放 /tmp 等重启即失的临时目录；后续补充证据链、修复方案、测试覆盖等追加在同一份报告上，形成单一审查档案而非散落多份文件。

- 机器生成的回执/报告正文不得内嵌状态机权威标记（如 `[factory:rejected]`）：机器状态由标签承载，正文一旦含有会被状态机子串匹配的权威标记，将以最高优先级钉死状态、永久关闭复核/重投通道；权威标记通道仅保留给人工手动覆盖（人写人删）。
- 自动化裁决的拒绝输出（issue triage 拒绝、门禁拦截等）同样适用本规范：必须附回执评论，逐条给出拒绝依据（判据）与需补充材料/重投指引；只落标签不发评论的静默拒绝不可审计，剥夺了人工介入所需的上下文。

- 并发子 agent（如 herdr 并行盘点）产出的行号类证据，须由主会话对关键引用抽查复核后方可写入正式报告；未经复核的 `文件:行号` 引用不得直接采信（实测盘点产物曾出现行号偏差）。
- 报告所依赖的中间产物（盘点报告、录制样本、比对基线等）不得停留在 /tmp 等易失目录，交付时应随报告归档至仓库持久位置，并保证引用路径相对可解析，避免重启丢失与追溯链悬空。

- 报告及相关文档中的跨仓/跨目录引用一律使用相对路径（以文档所在目录为基准），禁止绝对路径与依赖运行时 cwd 的裸前缀；被引用文档移动位置时须同步更新全部引用点并验证可解析。
- 横切能力（traceId/MDC/日志/鉴权）类审查结论，必须覆盖依赖 jar 的自动装配（`spring.factories` / `AutoConfiguration.imports` 注册的 Filter/Interceptor），仅 grep 项目源码会遗漏 starter 注入组件导致误判（实例：traceId 断裂 P0 评论被反汇编证据推翻后关闭）。

- 批量修改（正则替换、批量删除、注记清理）后必须做副作用走查：先对照变更前备份 diff 限定改动面，再机械扫描典型损伤（空括号/半空括号、双标点、悬空破折号、括号配对计数、表格列错位、误删相邻正文）；每处损伤须对照备份归因，区分「本次变更引入」与「既有损伤」——两者修复决策不同
- 迭代更新既有审查报告时，旧结论必须逐项按当前实际状态复核：用 git show/log 验证配置与 DDL 的真实入库提交，区分「工作区未提交状态」与「HEAD 已提交状态」；未经复核的旧指控不得原样带入新版报告，防止把已被远端修复或本就误报的问题重复上报。

- 更新既有审查报告时，须逐项复核旧指控并更新状态（已修复 / 仍在 / 误报更正）；复核确认的误报要显式更正并附证据（如 `git show` 回溯证明配置在更早提交已存在），不得静默删除或原样沿袭。
- 工作区存在未提交变更时，报告必须先声明基线（HEAD commit + 工作区是否干净）；事实类指控（配置缺失、DDL 重复建表等）须先用 `git fetch`/`git show` 对照远端最新状态与所指提交内容核实后再定级，避免把本地混合状态或过期本地认知误报为已提交代码缺陷。

- 更新既有审查报告时，须逐项复核旧指控的现状并亲自核实原始证据（git show / 直接读文件），不轻信子代理报告或 commit message；发现误报须在报告中显式标注"误报更正"及原因，不得静默删除或延续错误指控。
- 审视工作区未提交变更须逐文件定性为「真修复 / 倒退 / 门禁」再决定去留，不得一刀切丢弃或保留：与远端已合入的平行方案重叠的本地变更多为倒退，但其中对远端方案仍必要的配套修复（如分片键兜底填充、守护测试）应保留并适配远端新形态。

- 提交说明与 diff 实际不符时（如声称新增表但 DDL 中无此表），先追查该文件的提交历史再定性：先建后删可能是有意的方案收敛回退（如独立表改为复用既有表存储），不得直接断言为「变更丢失」或缺陷。
- 现状类指控（配置缺失、DDL 重复建表等）发布前，必须先以 `git show HEAD:<path>` / `git log -p` 核实仓库基线：本地工作区混有未提交或 stash 恢复的变更时，工作区现状 ≠ 远端 HEAD 现状，历次审查中 config-groups「空值」、wop_be_svc「重复建表」两指控均因直接 grep 工作区而误报。

- 每条发现必须附可独立复核的证据链：规格/规范原文逐字 → 代码原文逐字（file:line）→ 验证命令与输出，并标注验证等级（V1 亲验 / V2 抽验 / V3 子代理未复验），V3 断言须明示置信级别，防止误报
- 「与规范一致」的结论同样要附反向证据（实测代码原文），证明一致是验证出来的，而非默认放行
- 每条审查意见先实测取证再裁定：语法类用 `bash -n` 等工具实测、依赖类查仓库实际存在性；确认为误报的意见不盲改代码，逐条回评说明依据，防止「按建议改」破坏实际功能。

- 机器生成的回执/报告正文不得内嵌状态机权威标记（如 `[factory:rejected]`）：机器状态由标签承载，正文一旦含有会被状态机子串匹配的权威标记，将以最高优先级钉死状态、永久关闭复核/重投通道；权威标记通道仅保留给人工手动覆盖（人写人删）。

- 每个审查维度显式给出结论：有发现按「严重级 + 标题 + 文件:行号 + 证据摘录 + 修复建议」输出；无发现明确写「无新发现」——沉默缺省使读者无法区分「未检查」与「检查后无问题」。
- 审查结论应记录核验时点（文件 mtime 或内容指纹）：并行修复窗口中审查对象可能在报告出具后被修改，复核时先比对 mtime/指纹变化再决定重验范围，防止过期结论外发。

- 否定性结论（未落地/不存在/零残留）必须以 Read/Glob 直读原文复核后方可出具：grep 零命中可能是命令链短路（`&&` 前序命令非零退出）、反引号/通配转义差异造成的假象——凡零命中驱动的否定性结论，先补一次原文读取再下结论。
- 更新既有审查报告时，须逐项复核旧指控并更新状态（已修复 / 仍在 / 误报更正）；复核确认的误报要显式更正并附证据（如 `git show` 回溯证明配置在更早提交已存在），不得静默删除或原样沿袭。

一份审查报告是一张收据：读者凭它回答三个问题——**结论是什么、依据是什么、
这份报告证明了什么/没证明什么**。不声明自身盲区的报告会被当成全面事实。

### 结论与证据纪律
- 修复方案若取消既有兜底（如按 4xx 状态码豁免重试、直接落失败表），必须先核对业务送达原则并做误判损失不对称分析：HTTP 状态码无法可靠区分永久/暂时失败，误砍重试会不可恢复地丢失业务送达，误保留仅多几次低成本调用；不得仅凭状态码经验分类下结论。

### 结构与决策呈现

- 供跨团队评审的变更/冻结清单应做成回填式文档：每项含结论/日期/签字人栏，开放问题预置候选方案与推荐项（可附"评审前需确认事实"清单），使其可直接充当评审纪要与签字载体。
- 修复建议或权衡评估存在多个可行方案时，应编号呈现（方案A/B/…）、列各自利弊与适用条件，并给出明确推荐项及理由，让决策方可以逐条快速裁定（如"采用方案A修复R1"式决策）。

### 语义与验收

- 审查中遇到绝对语义措辞（恰一次、零丢失、实时生效等）应质疑其可实现性：能落地的写成可验证语义并注明兜底机制（如"幂等拦截 + 至少一次链路 + 消费方幂等头兜底"），不能兑现的降级措辞，避免留下无法验收的承诺。

## 五段式结构【强制】

按以下顺序组织，段落可合并但不可缺位：

### 1. 结论先行（重新定性）

- 第一句话给 **verdict + 定性**，不是症状复述
- 好例：「这是一个越界写库问题，不是命名不规范」（结论 + 升维定性）
- 坏例：「这里可能有点问题，建议看看」（无结论、无定性）
- 分级对齐 guard 家族：🔴 阻断 / 🟠 需处理 / 🟡 建议 / 🟢 通过

### 2. 依据（违反的不变量）

- 引用**具体规范条款**：steering 文件 + 条款标识（如 `database-design-specification §六、索引`、
  `rule_code=DEP_DIRECTION`），不接受「不符合最佳实践」这类无出处依据
- 一句话陈述应然状态（该成立的不变量），再指出偏离点

### 3. 证据 + 可执行建议

- 证据精确到 `file:line`（或 DDL 片段、SQL 语句），给证据链而非结论性描述
- 建议精确到**可直接执行**：给出修正后的 DDL/代码片段或明确步骤，
  不给「建议优化」级别的空话
- 自动检查已覆盖的项不重复展开，引用脚本输出即可

### 4. 关联

- 关联受影响的其他规范/模块（如「该索引缺失同时违反测试规范 §性能基线」）
- 只列**有因果**的关联，不为了显得全面而堆砌

### 5. 证据边界【强制】

报告末尾固定段落，声明三类信息：

```
── 证据边界 ──
  已验证: <脚本检查 + 人工核对的项>
  未覆盖: <本次未检查/无法检查的项，及原因>
  置信度: <对上述结论的把握及限制条件，如「基于静态阅读，未运行验证」>
```

- **验证过的事实**与**推断**必须可区分；未覆盖项永不静默
- 对齐收据规范三态不变量：每项检查要么执行（结论入正文）、要么显式跳过（入未覆盖）、
  要么拒绝（说明原因），不得消失

## 禁止事项

❌ - 报告更新后残留已被推翻的旧结论或「v1/v2 演进」叙事（如「此前误报为静默」）——多轮核查后必须清除中间结论，全文以最终态自洽、风险统一编号，避免旧表述误导后续读者
❌ - 否定性/存在性断言（如「X 域无事件发布」「无事务保障」）未经全仓反证搜索（对正向证据做全量扫描，如所有事件发布调用点）就写入结论——此类断言实测误报率最高，落笔前必须先搜索能推翻它的证据，并附搜索方式说明

- ❌ 无结论的探索式叙述（审查报告不是思考过程记录）
- ❌ 用修辞包装代替证据（排比、格言、升维叙事只在有助于定性时使用，不替代依据）
- ❌ 假装权威：没跑过脚本就说「脚本已通过」；没验证就写确定语气
- ❌ 静默缩窄范围：少查了什么必须写进「未覆盖」

## 示例

```markdown
🔴 阻断：这是一个跨层状态改写问题，不是风格问题。（1. 结论+定性）

违反 GTSP 01-project-structure §分层依赖：adapter 层不得直接改写聚合状态，
状态变更必须经领域服务。（2. 依据/不变量）

证据：OrderController.java:88 `order.setStatus(PAID)`，
绕过 OrderDomainService.pay()（该路径存在，见 OrderDomainService.java:31）。
建议改为注入 OrderDomainService 并调用 pay()，参考同包 PayCallbackListener.java:45
的合规写法。脚本已检出（STATE_FIELD_LEAKAGE），本条为人工确认 + 修复路径。（3. 证据+建议）

关联：修复后影响回归范围见 impact-guard 报告（OrderAgg 为聚合根，🟡 警告级）。（4. 关联）

── 证据边界 ──
  已验证: 分层脚本巡检通过、状态泄漏项人工核对
  未覆盖: 值对象不可变性、聚合边界合理性（需结合业务上下文人工判断）
  置信度: 修复路径基于静态阅读，未运行编译验证
```
