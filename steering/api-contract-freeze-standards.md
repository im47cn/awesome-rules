# API 契约冻结规范

> 来源：open-platform-admin 回调中心 MR !5 审查根因沉淀（2026-09）。
> 约束前端与后端的契约协作时序：**先冻结，再实现**。条款分【强制】/【推荐】两级。

## 1. 冻结范围与判定

### 【强制】契约未冻结字段名的端点禁止实现——mock 也不许先写

一个端点在被实现（进入 mock 或 `src/api`）之前，以下五项必须已在契约文档
（如 `api-contracts.md`）中**逐字段冻结**：

1. method
2. path
3. 请求参数名（含嵌套层级）
4. 响应信封（成功/失败的外层结构）
5. 响应字段名（含嵌套层级）

冻结 = 契约文档中逐字段列出且双方（前端 + 后端）已确认。只写了端点
method + path、没列字段名，不算冻结。任一项缺失 → 禁止动手写 mock
或 API 封装。

**为什么**：MR !5 审查根因——契约文档只冻结了约 20% 的字段名，mock 按
前端想象实现，本地全部自测通过；结果是 mock 把前后端**全部**参数名/
字段名不匹配（约 20+ 处 🔴）掩盖到联调期才集中爆炸。mock 越同构
（见前端规范 §1），凭想象写的 mock 就越像真的，掩盖得越深——因为
前端拿假字段名渲染出了真页面。

```
❌ 契约文档只有 POST /api/callback/subscribe 一行
❌ → 直接写 mock 返回 { id, url, status }（前端猜的字段名）
❌ → src/api/subscribe.ts 按猜的字段名封装

✅ 契约文档冻结：POST /api/callback/subscribe
✅   请求 { subscribeUrl, channel }
✅   响应信封 { code, message, data }
✅   data { subscriptionId, callbackUrl, status }
✅ → 再写 mock / src/api，字段名从契约照抄
```

## 2. 实现前 checklist

### 【强制】每个新端点动手前过四步

```
1. 查契约   api-contracts.md 中检索该端点，核对 method / path /
            请求参数名 / 响应信封 / 字段名五项是否全部冻结
2. 补冻结   缺项 → 先推后端在契约文档补齐并确认，涉及不兼容
            变更时 bump 契约版本；这一步完成前不写任何代码
3. 再实现   写 src/api 封装与 mock，字段名从契约逐字段照抄，
            不增不改名
4. 过守卫   contract:check 类守卫（存在时）必须通过；无守卫的
            项目在 MR 描述中附「契约行号 ↔ 实现文件」对照
```

**为什么**：四步的顺序就是「先冻结再实现」的时序强制。第 2 步把
「契约缺失」路由到正确的责任方（后端补冻结），而不是前端替后端
想象接口长什么样。

### 【推荐】守卫机械化：mock / src/api 与契约做静态对照

有人力接线时，给仓库接 contract:check 类守卫：从 `src/api` 提取
端点与字段名，与 `api-contracts.md` 冻结表做静态 diff，不一致即红。
此规范前两条依赖人记忆 checklist，守卫把「照抄不漂移」变成机器
判定——符合本仓「标注强制的条款应同步评估可机械检查性」原则。

## 3. 契约缺失时的正确动作

### 【强制】先冻结再实现，禁止先实现后补

契约缺失时的正确动作是**推动冻结**（找后端在契约文档补齐并确认），
而不是先按前端想象实现、联调后再回补契约文档。「先实现后补」
产出的契约文档只是对既有代码的事后描述，失去了冻结意义——它
冻结的是想象，不是双方共识。

**为什么**：MR !5 的字段名不匹配能存活到联调，正是因为走了
「先实现后补」路径：mock 与 src/api 同源于前端想象，自洽且自测
全绿，没有任何环节暴露与后端的分歧。契约冻结的价值恰在实现
**之前**制造一次前后端对表。

### 【推荐】字段名歧义在冻结阶段消解

冻结时后端若拿字段名歧义（驼峰/下划线、缩写与否）不当回事，前端
应在冻结阶段提出并定死命名，不留给联调期靠报错发现。
